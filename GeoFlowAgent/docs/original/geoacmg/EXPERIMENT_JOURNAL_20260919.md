## 2. 사고와 복구 — 실험 이전에 해결해야 했던 것

### 2.1 OOM 붕괴 (10:18~10:41Z)

geometry 15런 중 **9런이 죽어 있었다.** 원인은 연결 문제가 아니라 컨테이너 메모리 한계였다.

- `free` 는 호스트 메모리(503GB, 여유 377GB)를 보여준다. 실제 한도는
  cgroup v1 `memory.limit_in_bytes` = **120.0 GiB** 다.
- `compare-value-geometries` 1런의 anon-rss 는 실측 **25~31GB**.
- `geometry_pool.sh` 가 GPU 당 3개씩, 풀이 둘이라 **동시 6런 ≈ 168GB** 를 요구했다.
- 워커가 OOM 으로 죽으면 슬롯이 비어 풀이 즉시 다음을 띄웠다. 죽고-띄우고가 반복됐다.

**조치**: 풀 스크립트를 종료해 새 워커를 막고, 생존 3런은 유지. 117.2 → 88.8 GiB.
**이후 OOM 재발 0건.**

### 2.2 구조 개선 — 로딩 15회를 3회로

메모리 프로파일을 실측하니 런당 29GB 의 정체는 임베딩 캐시가 아니었다.
캐시는 `np.load(..., mmap_mode="r")` 로 올바르게 메모리 매핑돼 있다(`embeddings/cache.py:408,443-445`).
지배적 할당은 `processed/examples.jsonl` 6.39GB(448,704행)를 `read_jsonl` 이
파이썬 dict 448,704개로 펼친 것이다(`training/search_features.py:150`). 행당 55,799바이트
(JSON 원문 대비 3.9배), 합계 **약 23.3 GiB**.

그런데 `compare_value_geometries` 는 `shared_store` 를 **한 번만** 만들어 모든 (거리, 시드)
조합에 `_store_override` 로 넘긴다(`training/value.py:1508, 1525`). 즉 한 프로세스가
여러 조합을 돌면 **로딩 1회 · 29GiB 1벌**로 끝난다.

**시드별로 3배치로 묶어 재가동했다.** 수치 동일성은 `seed_everything(seed)`
(`value.py:1040`)가 매 run 시작에 RNG 를 전부 리셋하므로 보장된다.

### 2.3 경로 함정 제거

워커는 `--output-dir geometry_parts/{e}-{s}` 를 줬는데 코드는 run 디렉터리를
`output_dir/{energy}/seed-{seed}` 로 계산한다(`value.py:1516`). 그래서 15개를 한 트리에서 볼
방법이 없었고, **그 상태로 집계했다면 해시 검증·재사용이 아니라 15런 전부 재학습**이었다.
새 배치는 처음부터 `checkpoints/geometry_comparison/{energy}/seed-{seed}` 에 쓰게 했다.

### 2.4 동일성 검증

구조를 바꿨으므로 수치가 같은지 증명해야 했다. 마침 대조군이 있었다 —
`train_value` 는 사고 전 cosine·seed17 을 **개별 프로세스로 끊김 없이** 돌린 결과이고,
`geometry_comparison/cosine/seed-17` 은 같은 조합을 **OOM 으로 죽었다 재개하고
shared_store 배치 안에서** 돌린 결과다.

## 4. 실험 1 — 메커니즘: 학습된 에너지가 raw 거리의 실패를 고치는가

### 왜

probe 의 두 사실(선형 읽기는 성공 / raw 코사인 정렬은 실패)이 서로 긴장한다.
학습된 거리 헤드가 채울 자리가 정확히 거기인데, 그 자리가 실제로 채워지는지 아무도 재지 않았다.
**이것이 C1(표현)과 C4/C5(기하·계획기)를 잇는 단 하나의 숫자다.**

### 방법

참조 구현을 그대로 따르고 **정렬 기준 하나만** 바꿨다.

| 항목 | 구현 |
|---|---|
| 행 선별 | `runners.load_probe_table` 과 동일 (`value_known_mask` 참 AND `optimal_actions` 비어있지 않음) |
| 유전자 | `row["group_ids"]["entity"][0]` (`runners.py:53`) |
| 깊이 | `runners._state_depth(row["state"])` |
| 쌍 구성 | `probes.depth_matched_pairs` — 같은 task·같은 depth 안의 쌍만, V\* 가 같으면 제외 |
| raw 정의 | `1 − cos(state_emb, goal_emb)` |
| 통계 | `inference.paired_contrast`, 유전자 클러스터 부트스트랩 2000회 |
| **바뀐 것** | 정렬 값만 `energy_head(encode_entity(state), encode_entity(goal))` 로 |

같은 행·같은 버킷·같은 열거 순서이므로 per-pair 정확도가 **원소별로 짝지어진다.**
dev 에서만 평가했다(모델이 train 으로 학습했으므로).

**코퍼스 (fail-loud: 제외를 전부 보고)**: dev 상태 112,128 → 사용 31,050.
제외는 `optimal_actions` 없음 81,078건(72.3%), `value_known_mask` 거짓 0건.
쌍 141,517개, 유전자 클러스터 **47개**.

### 결과

| | 정렬 | raw 대비 [95%] | 우연 대비 [95%] |
|---|---:|---|---|
| **raw 코사인** | **0.5055** | — | **+0.0055 [−0.0347, +0.0309]** |
| pair_mlp | 0.8266 | +0.3210 [+0.2908, +0.3538] | +0.3266 [+0.3115, +0.3406] |
| directed_quasimetric | 0.7837 | +0.2782 [+0.2367, +0.3105] | +0.2837 [+0.2551, +0.3032] |
| poincare | 0.7685 | +0.2629 [+0.2075, +0.3056] | +0.2685 [+0.2238, +0.2912] |
| cosine | 0.7367 | +0.2311 [+0.2006, +0.2655] | +0.2367 [+0.2168, +0.2546] |
| euclidean | 0.5870 | +0.0815 [+0.0331, +0.1365] | +0.0870 [+0.0540, +0.1170] |

**읽는 법**
- **raw 코사인은 우연을 넘는다고 말할 수 없다** — 구간이 0을 포함하므로 UNRESOLVED.
  "정보가 없다"가 아니라 "이 설계로는 넘는다고 못 한다"이다.
- 학습된 에너지 **다섯 종 전부** raw 대비 0을 배제한다. euclidean 도 포함된다.
- 다만 크기가 4배 가까이 벌어진다(pair_mlp +0.3210 vs euclidean +0.0815).

### 이 과정에서 잡은 내 오류

첫 실행본이 참조 구현과 **세 곳** 달랐다 — 행 선별이 `value_star is not None`(참조는
`value_known_mask` + `optimal_actions`), 깊이가 자체 휴리스틱, 그리고 유전자 키가 없어
`task_id` 로 폴백해 **클러스터가 유전자 47이 아니라 task 584** 였다. task 클러스터링은
유전자 안의 상관을 무시해 구간이 실제보다 좁다(반보수적). 그 판에서는 euclidean 의 raw 대비
차이가 0을 포함해 "유클리드만 못 고친다"로 읽힐 뻔했다. 수정 후 그 결론은 사라졌다.

## 5. 실험 2 — 분해: 일하는 것은 에너지 공식인가 trunk 인가

### 왜

에너지는 학습된 좌표 z = `encode_entity(x)` 위에서 계산된다. 따라서 "에너지 공식이 일한다"와
"trunk 가 만든 좌표가 일한다"가 분리되지 않았다. trunk 가 이미 정렬 가능한 공간을 만들어
놓았다면 에너지 공식은 장식일 수 있다.

### 방법

체크포인트마다 **같은 쌍** 위에서 세 가지로 정렬했다.

- (a) `model.energy_head(z_s, z_g)` — 모델 자신의 에너지
- (b) `1 − cos(z_s, z_g)` — z 위의 평범한 코사인 (에너지 헤드 제거)
- (c) `‖z_s − z_g‖²` — z 위의 평범한 제곱 L2

store 1회 적재로 15 체크포인트를 전부 처리(체크포인트당 2.4초).
**정합성 검증**: cosine arm 은 (a)=(b), euclidean arm 은 (a)=(c) 가 소수점까지 일치했다.

동시에 P1 이 이름에서 지목한 **raw L2** 기준선을 동결 공간에서 함께 쟀다.

### 결과 ① — 동결 공간의 raw 기준선 3종이 전부 우연과 구별되지 않는다

| 기준선 | 정렬 | 우연 대비 | |
|---|---:|---|---|
| raw 코사인 | 0.5055 | +0.0055 [−0.0347, +0.0309] | UNRESOLVED |
| raw 제곱 L2 | 0.5078 | +0.0078 [−0.0320, +0.0332] | UNRESOLVED |
| raw 내적 | 0.4966 | −0.0034 [−0.0406, +0.0223] | UNRESOLVED |

코사인만의 문제가 아니다. **동결 공간에서는 어떤 단순 지표로도 깊이 고정 정렬이 되지 않는다.**
동결 공간 진단: `effective_rank 10.28/768`, `mean_cos 0.9690`.

### 결과 ② — 에너지 헤드의 기여가 극단적으로 다르다

| energy | 자기 에너지 | cos(z) | 헤드 기여 | 학습 좌표 eff.rank |
|---|---:|---:|---:|---:|
| cosine | 0.7367 | 0.7367 | 0.0000 (구성상) | 11.7 / 64 |
| euclidean | 0.5870 | 0.5666 | +0.0204 | 12.1 / 64 |
| directed_quasimetric | 0.7837 | 0.6290 | +0.1547 | 11.8 / 64 |
| pair_mlp | 0.8266 | 0.4955 | +0.3311 | 11.7 / 64 |
| poincare | 0.7685 | 0.4200 | +0.3484 | 10.2 / 64 |

**pair_mlp 와 poincare 의 학습 좌표는 평범한 코사인으로 읽으면 우연 이하다** (0.4955, 0.4200).
그런데 자기 에너지로 읽으면 0.8266, 0.7685 다.

### 해석

**에너지 함수는 표현 위에 얹는 읽기 장치가 아니라 어떤 표현이 학습될지를 결정한다.**
trunk 와 에너지 헤드는 함께 학습되므로 trunk 는 *그 에너지에 맞춘* 좌표를 만든다.
보편적으로 좋은 공간을 만드는 것이 아니다.

동시에 경계가 생긴다 — 학습된 기하는 **자기 에너지로만 접근 가능한** 기하다.
임의의 지표로 질의할 수 있는 거리 공간이 아니다. 검색 인덱스로 쓰려면 같은 에너지를 들고 가야 한다.

> 출처: `findings/mechanism_decomposition.json`, `findings/decomposition_pairs.npz`

## 6. 실험 3 — C5 검정과 그 통제 (음성 결과)

### 왜

C5 는 "계획기 타당성과 표현 타당성은 같은 주장"이다. 에너지 5개를 단위로 상관을 보면 n=5 라
근거가 못 된다. 같은 질문을 **모델 안에서 task 를 단위로** 물으면 n=584 가 된다.

### 방법

task t 마다 x_t = 그 task 쌍에서의 깊이고정 정렬 정확도, y_t = 그 task 의 dev policy 정확도.
상관의 구간은 유전자 47 클러스터 재표집. 저장된 산출물만 사용(store 적재 없음).

### 1차 결과 — C5 지지처럼 보였다

```
euclidean    -0.037 · -0.108 · -0.128   전부 UNRESOLVED
cosine       +0.115(U) · +0.332 · +0.473
dqm          +0.532 · +0.312 · +0.558    3/3 0 배제
poincare     +0.530 · +0.311 · +0.543    3/3 0 배제
pair_mlp     +0.355 · +0.614 · +0.520    3/3 0 배제
통제: 동결 raw 정렬 vs policy  -0.051 [-0.194, +0.103]  UNRESOLVED
```

여기서 멈췄다면 "좋은 기하에서는 표현과 계획이 함께 간다 = C5 지지"로 보고했을 것이다.

### 통제 — 과제 난이도 인공물인지 가른다

둘 다 같은 모델이 같은 task 에서 낸 값이므로 "쉬운 task 는 둘 다 잘 된다"로 설명될 수 있다.
**모델 A 의 정렬을 다른 모델 B 의 계획과 짝지어** 같은 상관을 쟀다(15×15 = 225 조합).

```
A=B  (같은 모델)               평균 r = +0.3282
A≠B, 같은 에너지 다른 시드      평균 r = +0.3206
A≠B, 다른 에너지               평균 r = +0.3289
유클리드 제외:  A=B +0.4329  vs  A≠B +0.4174
```

**상관이 A=B 든 A≠B 든 동일하다. 모델 고유의 표현-계획 결합은 없다.**
1차 결과는 과제 난이도 인공물이다. **C5 의 강한 형태는 지지되지 않는다.**

### 그러나 해리가 남는다

```
정렬 출처별 평균 r          계획 출처별 평균 r
  pair_mlp   +0.480          dqm        +0.350
  poincare   +0.450          pair_mlp   +0.345
  dqm        +0.427          euclidean  +0.327
  cosine     +0.325          poincare   +0.317
  euclidean  -0.044          cosine     +0.300
```

누구의 **계획**을 쓰든 상관이 같다. 누구의 **정렬**을 쓰느냐는 결정적이고 유클리드만 −0.044 다.
과제 난이도라는 잠재 축이 있고 모든 모델의 계획이 그 축을 따르는데,
표현 수준 정렬이 그 축을 잡아내는 것은 **기하가 좋을 때만**이다.

## 8. 실험 5 — 제외 표본의 정체

정렬 실험은 dev 상태의 27.7% 만 썼다. 무엇이 빠졌는지 확인했다.

```
제외 사유:  optimal_actions 없음 81,078건 (value_known_mask 거짓은 0건)
제외 상태의 V*:  중앙 0.00 · 평균 0.00 · 범위 [0, 0]
사용 상태의 V*:  중앙 3.50 · 평균 3.03 · 범위 [2, 10]
```

**제외된 상태는 전부 V\*=0 — 이미 목표에 도달한 상태다.** 목표가 `report.ready == True` 이므로
보고서를 낸 뒤의 상태는 최적 행동이 정의되지 않는다.

**이 제외는 결과를 보수적으로 만든다.** 제외 상태(V\*=0)와 사용 상태(V\*≥2)를 같은 버킷에서
짝지으면 자명하게 쉬운 쌍이 된다. 그 쌍들이 빠졌으므로 보고값은 **과소평가 쪽**이다.

**남는 한계는 깊이 편중이다.** 사용률이 depth 0 에서 100%, depth 3 에서 29.7%, depth 6 에서 0%.
정렬 결과는 **궤적 전반부에 대한 진술**이고 후반부로 외삽하지 않는다.

## 10. 실험 7 — C4: 이 벤치마크에서 원리적으로 검정 불가

### 사전등록의 정의

```
per-task benefit(quasimetric − cosine) ~ β₁·ρ     + controls      ρ = 비가역성
per-task benefit(hyperbolic  − cosine) ~ β₂·δ     + controls      δ = Gromov 4점 δ
"기울기 β 와 CI 를 보고한다. 평균 승패가 아니라."
반증조건: 기울기 CI 가 0 을 포함하면 복잡한 기하가 불필요함을 확증
```

`04_STATUS.md` 는 이를 "조절변수 회귀 미배선"으로 적어 두었다. 배선을 시도했고
**왜 미배선이었는지** 찾았다 — 코드 누락이 아니라 **회귀할 변동이 데이터에 없다.**

### 방법

`examples.jsonl` 448,704행에서 필요한 필드만 스트리밍으로 뽑아(49초, 6.4GB 전체 적재 회피)
task 별 상태 그래프를 복원했다. `action_successor_ids` 는 `{도구명: 후속 state_id}` 딕셔너리다.
task 2,337개, 해결된 간선 1,458,964개, 미해결 0.

### 결과 ① β₁ (비가역성) — 추정 불가

```
prefix 증가 1,458,964 (100.0000%) · 감소 0 · 동일 0
```

모든 간선이 증거를 누적만 한다. **순수 DAG 이므로 어떤 상태로도 되돌아올 수 없고
ρ = 1.0 이 모든 task 에서 상수다.** 분산 0 → 기울기 추정 불가.

### 결과 ② β₂ (δ) — 표준 정의로는 추정 불가, 대안들이 어긋난다

그래프가 구조적으로 동일하다: **노드 수 192 · 지름 7 이 모든 task 에서 같다**(sd 0.0000).
벤치마크가 같은 도구 10개·같은 최대 깊이로 task 를 만들므로 도달 가능한 상태 공간의
조합 구조가 전부 같다. 달라지는 것은 내용이지 그래프 모양이 아니다.

| δ 조작화 | 분산 | poincare−cosine | dqm−cosine |
|---|---|---|---|
| `delta_max` (표준 정의) | **고유값 1, sd 0** | 추정 불가 | 추정 불가 |
| `delta_p95` (고유값 2) | 있음 | **+0.02709 [+0.01782, +0.03684]** 0 배제 | +0.03836 [−0.03932, +0.11669] 0 포함 |
| `delta_mean` (범위 4%) | 미미 | +1.04622 [−0.02424, +1.93597] 0 포함 | +0.68755 [−0.08324, +1.49714] 0 포함 |

**`delta_p95` 로 재면 poincare 기울기가 0을 배제한다 — "C4 지지"로 쓸 수 있는 결과가 있다.
쓰지 않는다.** 사전등록은 "Gromov 4점 δ"라고만 적었고 어느 통계인지 지정하지 않았다.
세 조작화가 **추정불가 / 0배제 / 0포함** 으로 갈린다. 표준 정의인 max 는 값이 하나뿐이다.
따라서 0을 배제하는 판본은 데이터가 아니라 **사전등록되지 않은 분석 선택**이 만든 것이다.
금지사항 1 이 막는 지점이 정확히 여기다.

**결론: C4 는 이 벤치마크에서 사전등록된 형태로 검정할 수 없다.** 코드를 더 써도 안 된다.
판정하려면 그래프 구조가 task 마다 달라지는 코퍼스가 필요하다.

### 층별 짝지은 구간 — 역전은 지표와 에너지에 따라 다르다

| V\* 수준 균등 | **euclidean** | pair_mlp |
| 긴 과제 가중 | **euclidean** | poincare |

## 12. 실험 9 — 표현과 계획의 해리, 그리고 그 기제

### 해리

계획 수준의 역전이 **표현에서 오는가 계획에서 오는가**를 가르기 위해 같은 층화를 정렬에 적용했다.

정렬의 층별 짝지은 구간 (에너지 − euclidean):

| | V\*=3.5 | V\*=5.5 | V\*=7.5 | V\*=9.5 |
|---|---|---|---|---|
| cosine | +0.1999* | +0.1070* | +0.1430* | +0.0771* |
| dqm | +0.2694* | +0.1551* | +0.1641* | +0.0667* |
| poincare | +0.2859* | +0.1229* | +0.1302* | +0.0502 |
| pair_mlp | +0.3116* | +0.1885* | +0.2200* | +0.0964* |

**우위가 줄긴 하지만 어느 지평에서도 역전되지 않는다.** 같은 V\*=7.5 층에서:

```
표현(정렬):   pair_mlp − euclidean = +0.2200 [+0.1961, +0.2488]   기하 우세
계획(policy): pair_mlp − euclidean = -0.0123 [-0.0230, -0.0021]   euclidean 우세
```

**역전은 순수하게 계획 수준의 현상이다.** 표현은 긴 지평에서도 우위를 유지하는데
계획기가 그 우위를 성능으로 환전하지 못한다.

### 기제 — 두 정렬의 포화도 차이

`pairwise_regret_order_accuracy` 의 정의를 확인하니 **상태 수준 정렬의 행동 수준 대응물**이었다.

```python
for each state:
    for each pair of candidate actions with different oracle regret:
        pair_hits.append(sign(regret[left]-regret[right]) == sign(Q[left]-Q[right]))
```

| energy | 상태 간 정렬 | 행동 간 정렬 | policy |
|---|---:|---:|---:|
| euclidean | 0.5870 | 0.9254 | 0.8512 |
| cosine | 0.7367 | 0.9337 | 0.8613 |

## 13. 실험 10 — 용량 대조 (양방향 + 표현 수준까지)

### 왜

스윕 1위 pair_mlp 는 369,479 파라미터로 euclidean(335,942)보다 +33,537(+10.0%) 많다.
그 차이는 정확히 PairMLP 헤드 크기다(LayerNorm(256) 512 + Linear(256,128) 32,896 + Linear(128,1) 129).
"거리 공리를 버려서 이겼다"와 "파라미터가 많아서 이겼다"가 분리되지 않는다.

### 방법

`model_capacity_override` 로 `hidden_dim` 을 바꿔 양방향으로 막았다.
`train_value_geometry` 를 드라이버 스크립트에서 직접 호출하므로 **`src/` 무수정**,
`source_tree_sha256` 유지 → 기존 15런과 비교 가능. 6런에 store 공유.
파라미터 수는 학습 전에 모델을 직접 만들어 확인했고 기록값과 일치했다.

### 계획 지표 결과

| 대조 | policy | joint | regret@1 |
|---|---|---|---|
| **A** pair_mlp@h111(335,530) − euclidean@h128(335,942) | +0.0208 [+0.0160,+0.0256] | +0.0146 [+0.0100,+0.0191] | −0.0189 [−0.0259,−0.0121] |
| **B** pair_mlp@h128(369,479) − euclidean@h147(368,983) | +0.0106 [+0.0053,+0.0159] | +0.0055 [+0.0010,+0.0103] | −0.0302 [−0.0381,−0.0227] |
| **C** pair_mlp 용량 −9.2% | +0.0002 U | +0.0042 U | +0.0066 U |

A·B 의 여섯 구간이 전부 0을 배제한다. A 에서는 치료군이 파라미터를 412개 *적게* 쓰고도 이겼다.

### 표현(정렬) 결과 — D 가 결정적

| 대조 | 정렬 차이 | |
|---|---|---|
| A pair_mlp@h111 − euclidean@h128 | +0.2180 [+0.1730, +0.2584] | 0 배제 |
| B pair_mlp@h128 − euclidean@h147 | +0.2360 [+0.2080, +0.2661] | 0 배제 |
| C pair_mlp 용량 −9.2% | −0.0216 [−0.0355, −0.0142] | 0 배제 |
| **D euclidean 용량 +9.8%** | **+0.0036 [−0.0103, +0.0147]** | **UNRESOLVED** |

**euclidean 에 파라미터를 9.8% 더 줘도 정렬이 개선되지 않는다.**
euclidean 의 낮은 정렬은 용량 부족이 아니라 **기하 자체의 한계**다.

### 그리고 내부 일관성

```
용량 −9.2% 의 효과
  정렬:   -0.0216 [-0.0355, -0.0142]   0 배제      ← 움직인다
  policy: +0.0002 [-0.0051, +0.0052]   UNRESOLVED  ← 안 움직인다
```

**용량은 정렬에는 영향을 주지만 계획에는 주지 않는다.** 앞서 찾은 포화 기제와 정확히 일치한다.
서로 독립적으로 얻은 두 결과가 같은 그림을 가리킨다.

## 14. 실험 11 — 강건성

### leave-one-gene-out (47회)

논문의 방패인 파라미터 0개 대조를 흔들었다.

```
전체:        +0.1497 [+0.1076, +0.1870]
47회 범위:   [+0.1401, +0.1635]
47회 전부 구간이 0을 배제
```

### 파라미터 0개 대조가 무엇인가

에너지 헤드의 학습 파라미터를 세어 보니 스윕 안에 **자연 실험**이 있었다.

| energy | 에너지 헤드 학습 파라미터 | 총 파라미터 |
|---|---:|---:|
| cosine `1 − normalize(s)·normalize(t)` | **0** | 335,942 |
| euclidean `(s−t)².sum()` | **0** | 335,942 |
| poincare | 4,096 | 340,038 |
| pair_mlp | 33,537 | 369,479 |

cosine 과 euclidean 은 총 파라미터가 **완전히 같고** 에너지 헤드 학습 파라미터가 **둘 다 0**이다.
차이는 수식 한 줄뿐인데 정렬이 **+0.1497** 벌어진다.
에너지 헤드에 파라미터를 더해 얻는 것(poincare +0.0318, dqm +0.0470, pair_mlp +0.0899)보다 크다.

**기제 관측**: 이 공간은 `mean_cos 0.9690`, `effective_rank 10.28/768` 로 벡터들이 거의 같은
방향을 가리킨다. 제곱 유클리드는 노름 차이에 지배되는데 노름은 과제 신호를 거의 담지 않는다.
코사인은 노름을 버리고 방향만 본다.

### 하위집단

cosine 이 지는 유전자 6개 중 셋이 미토콘드리아였으나, MT 집단(7개) 전체로는 여전히 cosine 이
이긴다(+0.0622). **순위는 두 하위집단에서 동일하다.** 개별 유전자 수준의 우연이었고
과대 해석하지 않는다.

## 15. 실험 12 — 준거리와 도달 가능성 (가설)

## 21. 운영에서 배운 것

**병목 셋을 잡았다. 전부 "GPU 가 노는데 CPU 한 코어가 병목"이었다.**

1. 조합마다 프로세스를 띄워 store 를 15번 적재 → 시드별 배치로 **3회**
2. flow 평가의 전수 탐색 → root-only
3. 이미 코드에 있는 `GEOFLOW_STATE_FLOW_REPORT_TRAIN=0` 을 못 봄

**규칙으로 정리한다.**

- 동시 실행 수는 GPU 개수가 아니라 **cgroup 메모리 한도**가 정한다. `free` 는 호스트를 보여준다.
  120 GiB ÷ 31 GB ≈ 3 이 상한이다.
- 여유 판단은 **anon(rss)** 기준으로 한다. 페이지 캐시는 회수 가능하므로 빼야 한다.
- 긴 작업 전에 자원 프로파일만 볼 것이 아니라 **코드가 제공하는 축소 스위치를 먼저 찾는다.**
- 스크립트는 **진행 상황을 출력**한다. flow 가 3.5시간 침묵해 진행률을 알 수 없었다.
- 실행 전에 **API 를 정적 검증**한다. `store.view_dims` 가 property 인데 메서드로 호출한 버그를
  12분 적재 전에 잡았다.
- per-pair 벡터를 저장해 두면 클러스터 단위나 집계 방식을 바꿔도 재계산이 필요 없다.

**중요한 저장 위치 경고**: 모든 산출물이 `/tmp` (컨테이너 overlay, **임시**)에 있다.
`/root` 가 베슬 영구 스토리지지만 프로젝트 쿼터로 **여유가 200~300MB 뿐**이라 16GB 를 담을 수 없다.
컨테이너 재시작 시 소실되므로 외부로 내려받아야 한다.
